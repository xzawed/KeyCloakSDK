# Language Support Roadmap

This document defines the **language expansion strategy and priorities** for the Keycloak polyglot SDK. The languages currently supported are the nine — **Java**, **Python**, **TypeScript/Node**, **Go**, **C#/.NET**, **PHP**, **Rust**, **Ruby**, and **Kotlin** — and for all nine, design, implementation, unit tests, integration tests, and CI are complete, and all nine have since shipped a stable release through the human-gated publish step. This roadmap lays out (1) the principles of language expansion, (2) the prerequisite step-0 for actually publishing the existing SDKs, (3) the priorities and candidate clients for the next expansion languages, and (4) a per-language status matrix.

"Polyglot" means **multiple programming languages** and has nothing to do with natural-language localization (i18n).

## Strategy

- **Depth-first.** Rather than spreading thin across many languages, we finish the language we've started to the **same quality as Java/Python** before moving on to the next. We do not create low-quality tiers stamped out by code generation (codegen) — every language is hand-designed and hand-verified (including unit + integration tests, CI, and hardened JWT validation).
- **Isomorphic design.** Each language is idiomatic, but the concepts, layers, and flows are isomorphic. We keep the language-neutral API contract as the **single source of truth** and have each language implement it — see [CLAUDE.md §4](../../CLAUDE.md). Only idiomatic differences such as camelCase ↔ snake_case are allowed; the concepts, naming, and layering are kept aligned.
- **Wrap the best foundation + harden JWT ourselves.** For each language we wrap the most mature authentication (OIDC/OAuth2) and management (Admin REST) client behind a facade, but **for JWT validation alone we trust no library's defaults in any language** and layer our own hardening on top: algorithm pinning, rejecting `none`/unsigned, exact `iss` match, `aud` membership check, clock-skew limits, and DoS-safe JWKS refetch (addressing the CVE-2026-11800 class).
- **Preserve the coupling rule.** `admin` does not know about `auth` directly — so that swapping the underlying library does not ripple out to consumers. Two mechanisms achieve that independence and both are acceptable: a shared `TokenProvider` (a per-language interface/trait — Node · Rust · Ruby · .NET · Go), or `admin` owning its own client-credentials grant (Java · Kotlin · PHP · Python). See CLAUDE.md §4.
- **Exception boundary conversion.** The underlying library's exception/error types are always converted at the facade boundary to SDK exception types and never leak into the public API (for documented exceptions to this hiding, see [CLAUDE.md](../../CLAUDE.md) §4(b)).

## step-0 — Real publish of the existing SDKs (human-gated)

Before expanding to a new language, **actually publishing the 9 already-complete SDKs (Java, Python, Node, Go, .NET, PHP, Rust, Ruby, Kotlin)** was the top roadmap item, and it is now done. **All nine are now live as stable releases** — Packagist · PyPI · NuGet · crates.io · RubyGems · npm · Maven Central (Java and Kotlin) · the Go module proxy. Versions are per language, not fleet-wide; the per-language numbers are in the matrix below. Go went last on purpose: it needs no credential setup at all, but it has the weakest recovery of the nine — pushing the tag *is* the publish, the proxy cache is immutable, and the only remedy afterwards is a `retract` directive in a later release. **This axis is closed.** Each language spent a release candidate first, and each RC stays on its registry; what follows is ordinary versioning, not a first publish.

The procedure lives in **[DEPLOY.md](../../DEPLOY.md)** — do not copy checklists here. A previous copy in this file still said `git tag v0.1.0` / `py-v0.1.0` and "keycloak-sdk is not yet on PyPI" after those RCs had shipped. Use `scripts/release-readiness.sh [lang…]` and `scripts/release-trigger.sh <lang> <ver>` (both print only; they never push a tag).

## Expansion priorities

**Selection criteria**: ecosystem demand × availability of a mature client (actively maintained and Apache-2.0-compatible license). The auth·admin clients for each language below are **candidates, not final choices; at kickoff we re-verify maintenance, certification (OIDF, etc.), and license via deep research to finalize them**. In all cases, JWT validation is layered with our own hardening (library defaults not trusted).

> ⚠️ **Candidate · point-in-time snapshot caution — applies to *future candidate* rows only.** Version pins, MSRV numbers, toolchain/server target versions, archive dates, OIDF certification status, maintenance status, and CVE mentions written into a candidate row are **illustrative as of the day it was drafted** and are not verified against the repository. ⚠️ **The ✅ Done rows below deliberately carry no pins** — they drifted exactly as this caveat predicts (the table said admin-client 26.6.4 while the manifest had `~26.7.0`, Kover 0.9.8 vs 0.9.9, and the caveat's own `gocloak` v14 example contradicted the v13 in the row). Pins for shipped languages live in [CLAUDE.md](../../CLAUDE.md)'s dependency tables, where `scripts/check-docs.mjs` anchors them to the manifests. At the kickoff of each language cycle, they **must be re-verified** via deep research before being finalized — in the meantime the latest version/maintenance/certification status may have changed. This table fixes only direction (which family of clients is under consideration as a candidate); the hard numbers are not cited as established fact.
