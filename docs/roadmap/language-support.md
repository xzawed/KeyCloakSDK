# Language Support Roadmap

This document defines the **language expansion strategy and priorities** for the Keycloak polyglot SDK. The languages currently supported are the nine — **Java**, **Python**, **TypeScript/Node**, **Go**, **C#/.NET**, **PHP**, **Rust**, **Ruby**, and **Kotlin** — and for all nine, design, implementation, unit tests, integration tests, and CI are complete, with only the real publish step remaining behind a human gate. This roadmap lays out (1) the principles of language expansion, (2) the prerequisite step-0 for actually publishing the existing SDKs, (3) the priorities and candidate clients for the next expansion languages, and (4) a per-language status matrix.

"Polyglot" means **multiple programming languages** and has nothing to do with natural-language localization (i18n).

## Strategy

- **Depth-first.** Rather than spreading thin across many languages, we finish the language we've started to the **same quality as Java/Python** before moving on to the next. We do not create low-quality tiers stamped out by code generation (codegen) — every language is hand-designed and hand-verified (including unit + integration tests, CI, and hardened JWT validation).
- **Isomorphic design.** Each language is idiomatic, but the concepts, layers, and flows are isomorphic. We keep the language-neutral API contract as the **single source of truth** and have each language implement it — see [design spec §4](../superpowers/specs/2026-07-02-keycloak-multilang-sdk-design.md). Only idiomatic differences such as camelCase ↔ snake_case are allowed; the concepts, naming, and layering are kept aligned.
- **Wrap the best foundation + harden JWT ourselves.** For each language we wrap the most mature authentication (OIDC/OAuth2) and management (Admin REST) client behind a facade, but **for JWT validation alone we trust no library's defaults in any language** and layer our own hardening on top: algorithm pinning, rejecting `none`/unsigned, exact `iss` match, `aud` membership check, clock-skew limits, and DoS-safe JWKS refetch (addressing the CVE-2026-11800 class).
- **Preserve the coupling rule.** `admin` does not know about `auth` directly; the two are joined only through a shared `TokenProvider` (a per-language interface/trait) — so that swapping the underlying library does not ripple out to consumers.
- **Exception boundary conversion.** The underlying library's exception/error types are always converted at the facade boundary to SDK exception types and never leak into the public API (for documented exceptions to this hiding, see design spec §4).

## step-0 — Real publish of the existing SDKs (human-gated)

Before expanding to a new language, **actually publishing the 9 already-complete SDKs (Java, Python, Node, Go, .NET, PHP, Rust, Ruby, Kotlin)** is the top roadmap item. All are currently unpublished (`0.1.0`, Java is `-SNAPSHOT`), and because a publish is irreversible (you cannot re-publish the same coordinate/version), you must always verify the artifacts with a dry-run first. The full procedure follows the **9-language unified [DEPLOY.md](../../DEPLOY.md)** (readiness matrix + one-time setup per auth model + per-language detail, PR #30) — use `scripts/release-readiness.sh [lang…]` to check per-language readiness (secrets, registry, tags, OIDC pending-publisher) read-only, and `scripts/release-trigger.sh <lang> <ver>` to **only print** the exact tag-push command, dry-run, and checklist (both are human-gates that do not auto-push tags). The detailed checklists below are Java·Python examples (for the other 7, see DEPLOY.md §3).

> **Local install (unpublished state)**: Neither SDK is on a public registry yet, so `pip install keycloak-sdk` / Maven Central coordinate resolution **does not work yet**. Verify locally as follows — Java: `mvn -f java/pom.xml install -DskipITs=true` (Docker not required · → coordinate `io.github.xzawed:keycloak-sdk:0.1.0-SNAPSHOT`), Python: `pip install -e python` (or `cd python && python -m build`, distribution name `keycloak-sdk`).

### Java → Maven Central (`v*` tag → `.github/workflows/release.yml`)

- [ ] **Namespace verification (one-time)**: Log in to [central.sonatype.com](https://central.sonatype.com) with the GitHub account (`xzawed`) → verify/provision the `io.github.xzawed` namespace.
- [ ] **Central Portal token issuance (one-time)**: Account → Generate User Token → obtain username/password.
- [ ] **GPG signing key (one-time)**: Create with `gpg --gen-key` → distribute the public key to a key server (`--send-keys`) → export the private key armored (`private.asc`).
- [ ] **Register 4 GitHub Secrets**: `MAVEN_GPG_PRIVATE_KEY`, `MAVEN_GPG_PASSPHRASE`, `CENTRAL_TOKEN_USER`, `CENTRAL_TOKEN_PW`. (If unset, the workflow terminates at the deploy step with an authentication failure.)
- [ ] **Local pre-verification (no signing, no publish)**:
  ```bash
  mvn -f java/pom.xml -Prelease -DskipTests -Dgpg.skip=true package
  # → confirm *-sources.jar / *-javadoc.jar are generated in each target/ of core/auth/admin/keycloak-sdk
  ```
- [ ] **Publish trigger**: `git tag v0.1.0 && git push origin v0.1.0` → `release.yml` **sets the version from the tag value (stripping `-SNAPSHOT`)** and then runs `-Prelease deploy` → Publish from Central Portal Deployments. (The main POM stays `-SNAPSHOT`; **the tag determines the release version** — Central rejects SNAPSHOT, so this automatic substitution is essential.)

### Python → PyPI (`py-v*` tag → `.github/workflows/python-release.yml`)

- [ ] **Trusted Publisher setup (one-time, no secret needed)**: On [pypi.org Publishing](https://pypi.org/manage/account/publishing/), **you must register in advance as a Pending Publisher** (since `keycloak-sdk` is not yet on PyPI, use the account-level "Add a pending publisher") — Owner `xzawed` · Repo `KeyCloakSDK` · Workflow `python-release.yml` · Environment empty. Because it is OIDC authentication, there is no stored token.
- [ ] **Local pre-verification (no upload)**:
  ```bash
  cd python && python -m build
  # → confirm dist/keycloak_sdk-0.1.0-py3-none-any.whl + .tar.gz are generated
  ```
- [ ] **Publish trigger**: `git tag py-v0.1.0 && git push origin py-v0.1.0` → `python-release.yml` runs build + publish after passing verify (ruff·mypy·pytest).

> ⚠️ When bumping the version, bump Java `java/pom.xml` (and the modules') `<version>` and Python `python/pyproject.toml` `[project].version` together, and align the tags (`v*`/`py-v*`) accordingly. SemVer is based on the SDK's own API and is decoupled from the Keycloak / dependent-library versions.

## Expansion priorities

**Selection criteria**: ecosystem demand × availability of a mature client (actively maintained and Apache-2.0-compatible license). The auth·admin clients for each language below are **candidates, not final choices; at kickoff we re-verify maintenance, certification (OIDF, etc.), and license via deep research to finalize them** ([design spec §6.3·§10](../superpowers/specs/2026-07-03-keycloak-docs-and-language-expansion-design.md)). In all cases, JWT validation is layered with our own hardening (library defaults not trusted).

> ⚠️ **Candidate · point-in-time snapshot caution.** The version pins in the table below (e.g. `openid-client` v6, `gocloak` v14, `fschmtt` 0.42.x), MSRV numbers, toolchain/server target versions, archive dates, OIDF certification status, maintenance status, and CVE mentions are **all illustrative as of this document's drafting** and are not verified against the repository. At the kickoff of each language cycle, they **must be re-verified** via deep research before being finalized — in the meantime the latest version/maintenance/certification status may have changed. This table fixes only direction (which family of clients is under consideration as a candidate); the hard numbers are not cited as established fact.
