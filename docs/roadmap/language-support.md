# Language Support Roadmap

This document defines the **language expansion strategy and priorities** for the Keycloak polyglot SDK. The languages currently supported are the nine — **Java**, **Python**, **TypeScript/Node**, **Go**, **C#/.NET**, **PHP**, **Rust**, **Ruby**, and **Kotlin** — and for all nine, design, implementation, unit tests, integration tests, and CI are complete, with only the real publish step remaining behind a human gate — eight of them (all except Go) have since shipped a first release candidate. This roadmap lays out (1) the principles of language expansion, (2) the prerequisite step-0 for actually publishing the existing SDKs, (3) the priorities and candidate clients for the next expansion languages, and (4) a per-language status matrix.

"Polyglot" means **multiple programming languages** and has nothing to do with natural-language localization (i18n).

## Strategy

- **Depth-first.** Rather than spreading thin across many languages, we finish the language we've started to the **same quality as Java/Python** before moving on to the next. We do not create low-quality tiers stamped out by code generation (codegen) — every language is hand-designed and hand-verified (including unit + integration tests, CI, and hardened JWT validation).
- **Isomorphic design.** Each language is idiomatic, but the concepts, layers, and flows are isomorphic. We keep the language-neutral API contract as the **single source of truth** and have each language implement it — see [design spec §4](../superpowers/specs/2026-07-02-keycloak-multilang-sdk-design.md). Only idiomatic differences such as camelCase ↔ snake_case are allowed; the concepts, naming, and layering are kept aligned.
- **Wrap the best foundation + harden JWT ourselves.** For each language we wrap the most mature authentication (OIDC/OAuth2) and management (Admin REST) client behind a facade, but **for JWT validation alone we trust no library's defaults in any language** and layer our own hardening on top: algorithm pinning, rejecting `none`/unsigned, exact `iss` match, `aud` membership check, clock-skew limits, and DoS-safe JWKS refetch (addressing the CVE-2026-11800 class).
- **Preserve the coupling rule.** `admin` does not know about `auth` directly — so that swapping the underlying library does not ripple out to consumers. Two mechanisms achieve that independence and both are acceptable: a shared `TokenProvider` (a per-language interface/trait — Node · Rust · Ruby · .NET · Go), or `admin` owning its own client-credentials grant (Java · Kotlin · PHP · Python). See CLAUDE.md §4.
- **Exception boundary conversion.** The underlying library's exception/error types are always converted at the facade boundary to SDK exception types and never leak into the public API (for documented exceptions to this hiding, see design spec §4).

## step-0 — Real publish of the existing SDKs (human-gated)

Before expanding to a new language, **actually publishing the 9 already-complete SDKs (Java, Python, Node, Go, .NET, PHP, Rust, Ruby, Kotlin)** is the top roadmap item. **Eight are now live as release candidates** — Packagist `xzawed/keycloak-sdk` `0.1.0-rc.1` · PyPI `keycloak-sdk` `0.1.0rc1` · NuGet `Xzawed.Keycloak.Sdk` `0.1.0-rc.1` · crates.io `keycloak-sdk` `0.1.0-rc.1` · RubyGems `keycloak-sdk` `0.1.0.rc1` · npm `@xzawed/keycloak-sdk` `0.1.0-rc.2` · Maven Central `io.github.xzawed:keycloak-sdk` `0.1.0-RC1` · Maven Central `io.github.xzawed:keycloak-sdk-kotlin` `0.1.0-RC1` — and the remaining one (Go) is still unpublished (`0.1.0`). Go needs no setup at all, which is exactly why it is last: pushing the tag *is* the publish, and the only remedy afterwards is a `retract` directive in a later release. Because a publish is irreversible (you cannot re-publish the same coordinate/version), you must always verify the artifacts with a dry-run first. The full procedure follows the **9-language unified [DEPLOY.md](../../DEPLOY.md)** (readiness matrix + one-time setup per auth model + per-language detail, PR #30) — use `scripts/release-readiness.sh [lang…]` to check per-language readiness (secrets, registry, tags, OIDC pending-publisher) read-only, and `scripts/release-trigger.sh <lang> <ver>` to **only print** the exact tag-push command, dry-run, and checklist (both are human-gates that do not auto-push tags). The detailed checklists below are Java·Python examples (for the other 7, see DEPLOY.md §3).

> **Local install**: `pip install keycloak-sdk` **now resolves** — PyPI has `0.1.0rc1`, and pip falls back to the pre-release because no stable version exists yet. Maven Central coordinate resolution **now works too** — `io.github.xzawed:keycloak-sdk:0.1.0-RC1` resolves from Central (measured with `mvn dependency:get` in a clean container; unlike pip there is no fallback, so you must name that version). Verify locally as follows — Java: `mvn -f java/pom.xml install -DskipITs=true` (Docker not required · → coordinate `io.github.xzawed:keycloak-sdk:0.1.0-SNAPSHOT`, because the release workflow injects the tag version rather than keeping it in the POM), Python: `pip install -e python` (or `cd python && python -m build`, distribution name `keycloak-sdk`).

### Java → Maven Central (`v*` tag → `.github/workflows/release.yml`)

- [ ] **Namespace verification (one-time)**: Log in to [central.sonatype.com](https://central.sonatype.com) with the GitHub account (`xzawed`) → verify/provision the `io.github.xzawed` namespace.
- [ ] **Central Portal token issuance (one-time)**: Account → Generate User Token → obtain username/password.
- [ ] **GPG signing key (one-time)**: Create with `gpg --gen-key` → distribute the public key to a key server (`--send-keys`) → export the private key armored (`private.asc`).
- [ ] **Register 4 GitHub Secrets**: `MAVEN_GPG_PRIVATE_KEY`, `MAVEN_GPG_PASSPHRASE`, `CENTRAL_TOKEN_USER`, `CENTRAL_TOKEN_PW`. (If unset, the workflow terminates at the deploy step with an authentication failure.)
- [ ] **Local pre-verification (no signing, no publish)**:
  ```bash
  mvn -f java/pom.xml -Prelease -DskipTests -Dgpg.skip=true package
  # → confirm *-sources.jar / *-javadoc.jar are generated in each target/ of core/auth/admin/keycloak-sdk
  ```
- [ ] **Publish trigger**: `git tag v0.1.0 && git push origin v0.1.0` → `release.yml` **sets the version from the tag value (stripping `-SNAPSHOT`)** and then runs `-Prelease deploy` → Publish from Central Portal Deployments. (The main POM stays `-SNAPSHOT`; **the tag determines the release version** — Central rejects SNAPSHOT, so this automatic substitution is essential.)

### Python → PyPI (`py-v*` tag → `.github/workflows/python-release.yml`)

- [ ] **Trusted Publisher setup (one-time, no secret needed)**: On [pypi.org Publishing](https://pypi.org/manage/account/publishing/), **you must register in advance as a Pending Publisher** (since `keycloak-sdk` is not yet on PyPI, use the account-level "Add a pending publisher") — Owner `xzawed` · Repo `KeyCloakSDK` · Workflow `python-release.yml` · Environment empty. Because it is OIDC authentication, there is no stored token.
- [ ] **Local pre-verification (no upload)**:
  ```bash
  cd python && python -m build
  # → confirm dist/keycloak_sdk-0.1.0-py3-none-any.whl + .tar.gz are generated
  ```
- [ ] **Publish trigger**: `git tag py-v0.1.0 && git push origin py-v0.1.0` → `python-release.yml` runs build + publish after passing verify (ruff·mypy·pytest).

> ⚠️ When bumping the version, bump Java `java/pom.xml` (and the modules') `<version>` and Python `python/pyproject.toml` `[project].version` together, and align the tags (`v*`/`py-v*`) accordingly. SemVer is based on the SDK's own API and is decoupled from the Keycloak / dependent-library versions.

## Expansion priorities

**Selection criteria**: ecosystem demand × availability of a mature client (actively maintained and Apache-2.0-compatible license). The auth·admin clients for each language below are **candidates, not final choices; at kickoff we re-verify maintenance, certification (OIDF, etc.), and license via deep research to finalize them** ([design spec §6.3·§10](../superpowers/specs/2026-07-03-keycloak-docs-and-language-expansion-design.md)). In all cases, JWT validation is layered with our own hardening (library defaults not trusted).

> ⚠️ **Candidate · point-in-time snapshot caution — applies to *future candidate* rows only.** Version pins, MSRV numbers, toolchain/server target versions, archive dates, OIDF certification status, maintenance status, and CVE mentions written into a candidate row are **illustrative as of the day it was drafted** and are not verified against the repository. ⚠️ **The ✅ Done rows below deliberately carry no pins** — they drifted exactly as this caveat predicts (the table said admin-client 26.6.4 while the manifest had `~26.7.0`, Kover 0.9.8 vs 0.9.9, and the caveat's own `gocloak` v14 example contradicted the v13 in the row). Pins for shipped languages live in [CLAUDE.md](../../CLAUDE.md)'s dependency tables, where `scripts/check-docs.mjs` anchors them to the manifests. At the kickoff of each language cycle, they **must be re-verified** via deep research before being finalized — in the meantime the latest version/maintenance/certification status may have changed. This table fixes only direction (which family of clients is under consideration as a candidate); the hard numbers are not cited as established fact.

Exact unit/integration test counts are intentionally not hand-maintained here — the sole authority for a given point in time is each language's own CI job and coverage gate (see the per-language toolchain sections in `CLAUDE.md` / `.claude/rules/<lang>.md`); a number copied into this file drifts the moment CI's count changes, and this file previously carried stale, mutually inconsistent counts for every language. Java/Python/Node/Go/C#/Rust/Kotlin include Testcontainers integration tests against real Keycloak 26.6(.4), and **PHP·Ruby use a docker CLI shell-out fallback** (Windows native PHP/Ruby do not support the `unix://` socket transport required by their respective testcontainers bindings, so `docker run` is driven directly — it works identically on CI's ubuntu runners) to verify against the same real Keycloak 26.6; the E2E integration entry points are named `Full_flow` (.NET), `FullFlowIT` (PHP/Kotlin), `full_flow` (Rust/Ruby). A new language is considered "done" only after all the same 6 columns are filled at kickoff (depth-first). Node publish is triggered by a `node-v*` tag → `.github/workflows/node-release.yml` (npm Trusted Publishing / OIDC + provenance, human-gated). **Go publish has no registry — the `go/v*` tag itself is the release** (auto-cached by `proxy.golang.org`) → `.github/workflows/go-release.yml` (verify + GitHub Release + proxy warming, human-gated). C#/.NET publish is a `dotnet-v*` tag → `.github/workflows/dotnet-release.yml` (NuGet, requires the `NUGET_API_KEY` secret, human-gated). **PHP publish goes through a subtree-split mirror, not this monorepo** (`php-v*` tag → `.github/workflows/php-release.yml`, human-gated). Composer's VCS driver only reads the `composer.json` at a repository **root** and offers no way to point at a subdirectory, and this monorepo has no root `composer.json` (only `php/composer.json`) — so Packagist could never have watched this repository directly. The `split` job force-pushes `git subtree split --prefix=php` to the mirror repository `xzawed/keycloak-sdk-php` and tags it with a bare `vX.Y.Z` (Composer cannot parse `php-vX.Y.Z` as a version); that mirror is what is registered on Packagist, and it requires the `PHP_SPLIT_TOKEN` secret (fail-closed if unset). Rust publish is a `rust-v*` tag → `.github/workflows/rust-release.yml` (`cargo publish`, requires the `CARGO_REGISTRY_TOKEN` secret, human-gated). Ruby publish is a `ruby-v*` tag → `.github/workflows/ruby-release.yml` (RubyGems Trusted Publishing / OIDC, no stored secret, human-gated) — the first release needs a **pending** Trusted Publisher registered on rubygems.org beforehand. ⚠️ Do **not** hand-push the first gem with an API key as a workaround: a manual `gem push` bypasses `install-smoke`, the integration gate and the tag↔version guard, and burns the coordinate outside the pipeline (see [DEPLOY.md](../../DEPLOY.md) §2-B, which corrects the earlier advice). Kotlin publish is a `kotlin-v*` tag → `.github/workflows/kotlin-release.yml` (Maven Central Central Portal, a two-step gate where `publishToMavenCentral` stages and then a human manually releases from the Portal console, in-memory GPG via `ORG_GRADLE_PROJECT_*` secrets, human-gated).

Separate from this matrix, there is a harness ([`harness/`](../../harness/README.md), CI: [`.github/workflows/harness.yml`](../../.github/workflows/harness.yml)) that verifies and scores whether the 9 language SDKs behave isomorphically against real Keycloak on the same HTTP contract (v2) — **all 9 language (Go·C#·Node·Python·Java·PHP·Rust·Ruby·Kotlin) sample apps are complete** (each app consumes the SDK through the idiomatic framework net/http·ASP.NET Core·Express 5·FastAPI·Spring Boot·Slim 4·axum·Rack/Puma·Ktor/Netty). In addition to the legacy `./run.sh` (k6 load measurement/comparison only → `RESULTS.md`), `./verify.sh go dotnet node python java php rust ruby kotlin` gathers per-language conformance (contract compliance) · security (JWT hardening attack probes) · suites (each SDK's unit tests + coverage + lint) signals and produces a **4-dimensional weighted scorecard** (functional 30% · security 30% · coverage 20% · perf/isomorphism 20%, grades A~D) as `report/SCORECARD.md` (the perf/isomorphism dimension is **k6-wired** — the validate p95 relative score across languages). CI (harness.yml) is Plan A — on PR/push a fast Go smoke gate (`mvp-go`), and nightly (schedule 03:00 UTC) · manual (workflow_dispatch) it runs the 5-language k6 comparison (`all-langs`) and the 9-language comprehensive verification/scoring (`score-all`).

And one more: the **install-and-operate verification harness** ([`harness/install/`](../../harness/install/README.md), merged in PR #21 · Kotlin added in PR #26) **installs each SDK like a published package from a Docker local registry (Verdaccio·pypiserver·file-GOPROXY·BaGetter·nginx-.m2·gem-index·Satis·cargo-local-registry·mvn-repo-kotlin) without a real publish, and verifies it operates (quickstart+conformance+security) against real Keycloak** — a final pre-publish check of the install path of the publish artifact (manifest·metadata·dependency resolution) that source-path consumption does not verify. **All cells GREEN across all 9 languages in local measurement** (conformance 26/26 · security 9/9). `cd harness/install && ./install-verify.sh`. CI `install-all` job (nightly/manual · `INSTALL-MATRIX.md` artifact).
